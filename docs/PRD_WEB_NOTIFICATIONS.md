## Decisions (user, 2026-10-12)

1. **Base is `main`.** `prd/prd_web_moderation_tools` runs concurrently and also edits `client.ts`, `types.ts`, `en.json` and `Sidebar.svelte`; keep every notification addition in its own contiguous block in those files.
2. **Row design mirrors mobile**: upvote groups as compact Bluesky-style rows, replies and mentions as Voyager-style cards, subtle unread tint, all from Kelp's theme tokens (`src/app.css` `@theme`) and existing kit components, no new hex values. Built in the loop; the user tunes spacing afterwards.
3. **Preferences** live in a "Notifications" section of the existing `/settings` area: four toggles on `ToggleSetting.svelte`, backed by `getPreferences`/`putPreferences`, reached also by a gear link on `/notifications` (placement: decision 15).
4. **One list.** No Mentions tab or reason filter (the API has none).
5. **No row actions.** The whole row is one link that opens the thread (Navigation table). Amended 2026-10-18: reply and mention cards get Quick Reply (Row design).
6. **Placeholder copy** reuses the existing `comment.placeholder.*` strings; an unknown `status` uses the removed-by-moderator copy.
7. **Removed or deleted root post** (`rootPost.status` set, so no `community`): the card hides its header and shows the placeholder in the title position. A placeholder repeated in the same card is shown once.
8. **DID-only actors** (no `handle`, no `displayName`): "Unknown user", the `Avatar` default image, no `@handle` line.
9. **Unknown `reason` values are skipped.** Rows that fail the type checks in "API client" are skipped too.
10. **NSFW concealment per row** with a per-row reveal, keyed by row identity `<reason>|<record.uri>` (replies, mentions) or `upvote|<subject.uri>`.
11. **Accessible names use the actor's name** (display name, else handle), never the `@handle` line.
12. **"Displayed" means visible**: `/notifications` is mounted and `document.visibilityState === 'visible'`.
13. **Upvote heart is filled**, in the upvote colour.
14. **Sentry or other crash reporting is out of scope.** No telemetry is added.

Planner defaults, decided 2026-10-12 (the user confirmed 15, 16 and 18–27 and amended 17):

15. **Settings placement**: a fourth tab `/settings/notifications`.
16. **Bell when signed out**: shown, no badge, `href="/notifications"`, whose load redirects to login as Create does.
17. **Return from a thread opened from a row** (amended by the user): when the user follows a row link in the same tab and comes back to `/notifications` from that thread, by browser Back or by clicking the Notifications nav item or bell, the list is restored as it was: the loaded pages (rows with their read state, cursor, page-one `seenAt` boundary, reveal set) and the scroll position. Any other entry to `/notifications` loads page one as before: a fresh or full page load, a typed URL, or arriving from an unrelated page (leaving the opened thread's path for any page other than `/notifications` drops the saved list; query and hash changes on that path, such as a comment sort change, keep it). On a restore nothing reloads automatically: the restore-time unread count does not trigger the visible-return or count > 0 reload, and only a count rise observed after the restore reloads page one (the normal rule in "List and paging", chunk 20). A restore sends no `updateSeen`; only a page-one reload after it is marked seen. The saved list is dropped on logout or an account change (the owner rules in Session ownership; expiry keeps it as it keeps live rows) and on a full page reload (it lives only in memory). Contract: "Return restore" under List and paging; chunk 23.
18. **`/notifications` mounted with an expired session**: send nothing, show no rows, no spinner, no empty state and no error; the existing `SessionRecovery` UI handles re-auth; after re-login as the same account, page one loads.
19. **Expiry vs account change** (list owner, see "Session ownership" under List and paging): expiry blocks every send and every response acceptance but keeps the accepted rows of the same owner; logout or adopting a different account resets the list state.
20. **Signing out while `/notifications` is mounted**: the list state resets and nothing is sent; `logout()`'s existing `goto('/')` (`src/lib/feature/user/logout.ts`) stands.
21. **A page-one reload that fails while rows are shown**: keep the rows, show no error UI, log through the notification log helper (no URL, cursor or body), and the next trigger reloads; rows never marked seen stay markable by the next successful reload.
22. **End-to-end baseline**: the two-account scenario enables all four reasons for B, establishes a real displayed-and-marked-seen baseline (unread count 0) before A acts, and identifies scenario rows by the targets it created (Testing).
23. **Watermark with an unparseable `sortAt`**: the `updateSeen` watermark is the largest page-one `sortAt` that parses, sent as its raw string; if none parses, no `updateSeen` is sent; nothing reaches the UI.
24. **The `InvalidCursor` recovery load fails**: the current rows stay, the later-page Retry footer shows, the failure is logged, and Retry runs the recovery page-one load again.
25. **`/settings/notifications` while the session is expired**: as signed out (no tab, a login link, nothing sent), because `expireSession()` makes the current profile a guest.
26. **Reply or mention without `author`** (optional in the lexicon; the backend always sends it): "Unknown user", no `@handle` line, the `Avatar` default seeded with `record.uri`, and links built without an author ref (the link builders fall back to the URI authority DID).
27. **Live root without `rootPost.community`** (optional in the lexicon): the header keeps the reason line and the time but drops the community avatar and the `!community` line; the link name drops " in <!community>"; the href uses the DID fallback of placeholder roots (Navigation).

## Behaviour

### API client
- `src/lib/api/coves/client.ts`: add `NSID.listNotifications`, `getUnreadNotificationCount`, `updateNotificationsSeen`, `getNotificationPreferences`, `putNotificationPreferences` (values `social.coves.notification.listNotifications`, `.getUnreadCount`, `.updateSeen`, `.getPreferences`, `.putPreferences`) and `CovesClient` methods of the same names: queries via `this.xrpc.query`, `updateSeen` and `putPreferences` via `this.xrpc.procedure`. `listNotifications` takes `{ limit?, cursor? }` and the app always omits `limit` (server default 50).
- `src/lib/api/coves/types.ts`: `NotificationReason` (`'postReply' | 'commentReply' | 'mention' | 'upvote' | (string & {})`), `NotificationStatus` (`'deleted' | 'removedByModerator' | 'removedByServerAdmin' | (string & {})`), `NotificationActor` (`did` required; `handle`, `displayName`, `avatar` optional, per `social.coves.actor.defs#profileView`), `NotificationRootPost` (`uri`, `cid`, `status?`, `title?`, `labels?`, `thumbnail?`, `thumbnailAlt?`, `community?: CommunityRef`), `NotificationSubject` (`uri`, `cid`, `status?`, `preview?`, `labels?`, `thumbnail?`, `thumbnailAlt?`), `NotificationRecord` (`uri`, `cid`, `status?`, `excerpt?`, `createdAt?`, `labels?`, `thumbnail?`, `thumbnailAlt?`), `NotificationView` (`reason`, `sortAt`, `isRead`, `rootPost`, `subject?`, `record?`, `author?`, `upvoteCount?`, `recentUpvoters?`), `ListNotificationsResponse` (`notifications`, `cursor?`, `seenAt?`), `UnreadNotificationCount` (`{ count }`), `NotificationPreferences` (four required booleans) and `PutNotificationPreferencesInput = Partial<NotificationPreferences>`.
- Row validation at the boundary (`src/lib/feature/notification/rows.ts`): skip a row whose `reason` is unknown, whose `sortAt` is not a string, whose `isRead` is not a boolean, whose `rootPost.uri` is missing, a reply or mention without `record.uri`, or an upvote without `subject.uri`. Skip an upvote row with no `recentUpvoters` and a missing or zero `upvoteCount` (the server never sends one). The backend omits `recentUpvoters` for bridged-only groups (`omitempty`); the boundary normalises an omitted array to `[]`. Every other optional field (`author`, `rootPost.community`, `record.createdAt`, `upvoteCount`, texts, labels, thumbnails) may be absent on an otherwise valid row; the row is kept and rendered by Row design and decisions 26–27, never through an unchecked access.
- Errors are `XrpcError` (`src/lib/api/coves/xrpc.ts`); code branches on `status` and `errorName`: `InvalidCursor` (400, `listNotifications`), `AccountNotIndexed` (400, `updateSeen`, `putPreferences`). A 401 already expires the session through `covesCustomFetch` in `src/lib/api/client.svelte.ts` (`profile.expireSession`) and `SessionRecovery.svelte` prompts; callers check `isExpiredSessionError` (`src/lib/app/util/session-expired-error.ts`) and show no toast of their own for it.
- Logging: notification code logs only the NSID, HTTP status and `errorName`, through `log` (`src/lib/app/util/log`). It never logs a request URL, a cursor, a response or request body, a `sortAt`/`seenAt` value, a notification URI, or an Error object that is not an `XrpcError`. The proxy (`src/routes/api/proxy/[...path]/+server.ts`) and `hooks.server.ts` already log the path without the query string; keep it so.

### Unread badge and polling
- One app-lifetime store, `src/lib/feature/notification/unread.svelte.ts`, started once from `src/routes/+layout.svelte` in the browser only. It holds `count` (starts at 0) and a session key `${profile.current.did}|${profile.sessionGeneration}` (`src/lib/app/state/auth.svelte.ts`).
- Fetches `getUnreadCount` when a session is adopted (app start with a session, or login), every 30 s while signed in and `document.visibilityState === 'visible'`, once on `visibilitychange` to visible, once on window `focus`, on every navigation into `/notifications` (`afterNavigate`), after `updateSeen` succeeds, and after a preference save succeeds. At most one request is in flight; triggers during it are absorbed. The timer stops while hidden and while signed out or the session is expired (`profile.isAuthenticated` false).
- Signed out: no badge, no timer, no request. Logout, session expiry or a new session key sets `count` to 0 at once. **Request epoch** (used by the unread, preferences and list stores): each store keeps a counter that increases on every change of its owner key, expiry and the revival of the same generation included; a response is applied only if the key and the epoch at send time both still match, so a response sent before an expiry is discarded even when `beginSessionRevalidation()` and `syncFromServer` revive the same generation. A key change releases the single-flight latch, so the adoption fetch goes out at once. Each request carries a sequence number; the accepted-refresh signal publishes `{ key, sequence, count }` once per accepted response.
- A failed fetch (network, 5xx, 429, parse) keeps the last count, with no toast or banner.
- The bell is a `NavButton` (`src/lib/ui/navbar/NavButton.svelte`) in `src/lib/feature/shell/navbar/Navbar.svelte` with `href="/notifications"`, label `$t('nav.notifications')`, a Lucide `Bell` added to `src/lib/ui/kit/icon/index.ts`, and class `order-3` (between Create `order-2` and the profile menu `order-4`). That one Navbar is the sticky top bar at `md` and up and the bottom dock below `md` (`src/lib/ui/layout/Shell.svelte`), so it covers both layouts; the bell is shown signed in and signed out (decision 16), like Create.
- Bell: icon only (no text label), 20 px at every width, beside the profile avatar.
- Badge: a 15 px pill overlapping the bell's upper right as Bluesky's does (left edge at the icon's centre for one digit, a third in for longer counts), red (`bg-red-600 text-white`, `dark:bg-red-500`), no ring; hidden at 0; 1–99 as the number; above 99 (the API caps at 101, meaning "100+") "99+". It is rendered only in the browser after the first count, so server HTML never has a badge. The visible badge is `aria-hidden`; the link's accessible name becomes "Notifications, N unread" (N as shown) when the badge is visible.

### List and paging
- Route `src/routes/notifications/`: `+page.ts` sets `export const ssr = false` and redirects as `src/routes/create/post/+page.ts` does: signed out and not `profile.sessionExpired` → `redirect(302, loginUrl(url))` (`src/lib/app/util/login-url.ts`), which returns to `/notifications` after login. The load fetches nothing.
- Why client-side: the comparable per-account pages (`src/routes/profile/+layout.ts`, `ssr = false`, with `profile/(local_user)/blocks/*` loading in the browser) do not server-render account data. Notifications are per-user, change while the page is open, and must only be marked seen after they are on screen; keeping page one, later pages, reloads, recovery and session discards in one browser-side owner (`src/lib/feature/notification/list.svelte.ts`) also lets a failure render the page's own retry state instead of the root error page.
- The page creates a list state on mount, which fetches page one, unless the entry restores a saved list (decision 17, "Return restore" below). States: loading (kit `Spinner`); empty ("No notifications yet" / "Replies, mentions and upvotes will appear here.", `src/lib/ui/info/Placeholder.svelte`); page-one error ("Could not load notifications." with a Retry button, `message.retry`); later-page loading as a kit `Spinner` in a `role="status"` named "Loading more notifications" below the rows; later-page error as a footer with the same Retry. A 401 shows no error of its own (the recovery banner covers it).
- Header: title "Notifications" and a 44 px (`size-11`) gear link (Lucide `Settings`, accessible name "Notification settings") to the settings section.
- Infinite scroll always, whatever `settings.infiniteScroll`: an `IntersectionObserver` sentinel with a 300 px root margin, as in `src/lib/feature/post/feed/VirtualFeed.svelte`. Paging continues while `cursor` is present, including after a short or empty page; the sentinel re-triggers while in view. If a response repeats a cursor already requested in this list, paging stops and logs one warning without the cursor.
- Rows are deduplicated by identity; the first occurrence wins.
- `InvalidCursor` on a later page replaces the list with a fresh page one (new `seenAt` boundary, marked seen again if displayed). A second `InvalidCursor` before re-arming shows the Retry footer. A failed recovery load follows decision 24. The recovery load itself leaves recovery spent; it re-arms on a manual Retry, an ordinary (non-recovery) page-one reload, or an owner reset.
- Reload page one (replacing the whole list) when the unread count rises above the last value the page observed while displayed, when the document returns to visible and the next *accepted* unread refresh after that return reports a count above 0 (even if unchanged; the unread store publishes each accepted refresh with its owner key, sequence and count), and on every fresh entry, that is every mount that does not restore a saved list (which covers preference changes made in Settings). One reload at a time; a trigger during a load queues exactly one more. An owner transition (expiry, logout, account change) cancels a queued reload. Every page-one replacement and every owner transition starts a new list generation (the list's request epoch); a later-page success or failure sent under an older generation is discarded (no append, no cursor change, no footer, no recovery). There is no manual refresh control; a browser reload loads page one.
- Session ownership. `expireSession()` replaces `profile.current` with a guest (`src/lib/app/state/auth.svelte.ts`), so `${profile.current.did}|${profile.sessionGeneration}` changes on expiry; the list does not use that key as its reset rule. The list's owner is the authenticated `profile.current.did` its rows were requested under. Sends happen only while `profile.isAuthenticated`; a response is accepted only if, on arrival, `profile.isAuthenticated`, `profile.current.did` and `profile.sessionGeneration` equal their values at send time and the list generation is unchanged (so a response sent before an expiry is discarded after a same-generation revival). Expired (`profile.sessionExpired`): rows, cursor, boundary and reveal state stay, nothing is sent, nothing is accepted. Re-auth as the owner DID (new or revived generation): page one reloads, rows stay until it succeeds. Logout (signed out, not expired) or an authenticated different DID: rows, cursor, boundary, reveal state, recovery arm and queued reload are reset at once; for a different account page one loads. The unread store and the preferences store keep the `${did}|${generation}` key and reset on any change of it, expiry included.
- Return restore (decision 17). Save: when an in-app navigation leaves `/notifications` for the href of a rendered row (a same-tab row click, or browser Forward to that row's target), the list's plain data is saved in an app-lifetime in-memory store (`src/lib/feature/notification/return.svelte.ts`): owner DID, rows with their read state, cursor, page-one `seenAt` boundary, requested cursors and paging stop, recovery arm, reveal set, `window.scrollY`, and the target's path. Nothing in flight, no queued reload and no later-page footer is saved. Decide: a root-layout `beforeNavigate` sees every later navigation; one that stays on the target's path (query or hash change) keeps the save; one into `/notifications` of type `popstate` (Back) or `link` (bell, nav item) marks it for restore; any other drops it. Restore: the page takes the marked save once (taking clears it) and creates the list from it under a new list generation, with no page-one request, no `updateSeen`, no queued reload, and the unread `count` at restore as the last observed count; paging, reload triggers, recovery and the owner rules then run as for any list. Scroll: after SvelteKit's own scroll handling (`afterNavigate`) and once the restored rows are in the DOM (`await tick()`), `window.scrollTo` the saved `scrollY`, re-applied on animation frames until it holds or 500 ms pass, as `src/lib/feature/post/feed/restoration.svelte.ts` does. Drop: logout (signed out, not expired) or an authenticated different DID drops the save at once, even while `/notifications` is not mounted; expiry keeps it (a restore while expired shows the rows and sends nothing; re-auth as the owner then runs the owner reload); a full page reload loses it because it is never written to `sessionStorage`, `localStorage` or history state. Responses to requests sent by the list before the row was followed never reach the restored list.

### Seen state
- After page one is accepted and non-empty, once its rows are in the DOM (`await tick()`) and the page is displayed, call `updateSeen({ seenAt })` with the largest `sortAt` of page one (the largest that parses, decision 23), as the exact string the server sent. Never the client clock, never re-serialised through `Date`. If page one arrives while hidden, wait for `visibilitychange` to visible. Each page-one load marks at most once. Skip when page one is empty. A restored list (decision 17) sends no `updateSeen`; only a page-one reload after the restore marks. Do not send if the list generation changed since page one was requested (an owner transition, expiry included, or a newer page-one load), or if `/notifications` unmounted before the mark.
- Timestamps are compared at full fractional precision by `compareNotificationTimestamps(a, b)` in `src/lib/feature/notification/timestamp.ts`: the seconds part (with offset) via `Date.parse`, then the fractional digits right-padded to 9. `Date` alone keeps milliseconds and cannot order two `sortAt` values in the same millisecond. An unparseable input throws an error that does not contain the input.
- On success, refetch the unread count; the badge is never zeroed optimistically. Failures, including `AccountNotIndexed`, are silent apart from the log line in "API client".
- Page-one rows use the server's `isRead`. Rows from later pages are read when `compareNotificationTimestamps(sortAt, pageOneSeenAt) <= 0`, and all read when page one had no `seenAt`. A row whose timestamp cannot be compared keeps the server `isRead`.

### Navigation
Every row is an `<a href>` built with `postLink`/`commentLink` (`src/lib/feature/post/helpers.ts`). `rootRef` is `{ uri: rootPost.uri, community: rootPost.community }`; when `community` is absent (placeholder root), use `{ did: <rootPost.uri authority DID>, name: '' }`, which `communityRouteParam` (`src/lib/app/util/links.ts`) turns into the DID segment that the `[handle=handle]` matcher accepts; the post loader does not check the community segment and renders its own removed or unavailable state. A URI is a comment when its collection is `social.coves.community.comment`, otherwise a post. Web has no `?comment=` parameter; a focused comment is the comment permalink route `src/routes/c/[handle=handle]/post/[owner=actor]/[rkey]/comment/[commenter=actor]/[crkey]/`.

| Reason | Target |
|---|---|
| `postReply`, `commentReply` | `commentLink(rootRef, record.uri, author)` |
| `mention`, `record` is a comment | `commentLink(rootRef, record.uri, author)` |
| `mention`, `record` is a post | `postLink({ uri: record.uri, community: rootRef.community, author })` |
| `upvote`, `subject` is a comment | `commentLink(rootRef, subject.uri)` |
| `upvote`, `subject` is a post | `postLink({ uri: subject.uri, community: rootRef.community })` |

Placeholder rows navigate the same way. Ordinary link behaviour (middle-click, new tab) works because the row is a real link.

### Row design
Shared helpers in `src/lib/feature/notification/rows.ts`: actor name (`displayName` trimmed, else `usableHandle(handle)` from `$lib/types/atproto`, else "Unknown user"); placeholder copy (`deleted` → `comment.placeholder.deletedByUser`, `removedByModerator` → `comment.placeholder.removedByModerator`, `removedByServerAdmin` → `comment.placeholder.removedByAdmin`, anything else → `comment.placeholder.removedByModerator`); the upvote sentence; identity; href. Avatars are `src/lib/ui/generic/Avatar.svelte` with `url={actor.avatar}` (its `url` prop is required but may be `undefined`) and `alt={actor.did}`: with no `url` it renders its generated default, which uses `alt` as the seed. Times are `src/lib/ui/util/RelativeDate.svelte` with `publishedToDate` (`src/lib/ui/util/date.ts`), as `Comment.svelte` uses them, so the absolute-dates setting applies.

**Upvote group** (`UpvoteRow.svelte`), compact:
- Leading filled heart: `src/lib/ui/icon/AnimatedHeart.svelte` with `liked={true}` (its default `likedColor`, the upvote colour; no animation on mount).
- Avatar stack of `recentUpvoters` (up to 3, overlapping).
- Sentence, names bold, with `n` = `recentUpvoters.length` (after normalising an omitted array to `[]`) and `c` = `Math.max(upvoteCount ?? 0, n)`: `n = 0` → "**c people** upvoted your post" ("**1 person**"); `n ≥ 1` and `c > n` → "**alice** and **c−1 others** upvoted…" ("**1 other**"); otherwise list the names: "**alice**", "**alice** and **bob**", "**alice**, **bob** and **carol**". "your post" or "your comment" by `subject.uri`. Then " · " and the relative `sortAt`, unless a body renders (the time then sits at the top right).
- Below, for an upvote on the root post itself (`subject.uri` = `rootPost.uri`): the root post card. For a comment: `subject.preview` in a bordered quote box, muted, at most 3 lines, or the placeholder copy when `subject.status` is set; a trailing square `subject.thumbnail` when present, `alt` = `thumbnailAlt` or empty.
- When a body renders, the time stands apart at the top right instead of ending the sentence.

**Reply or mention** (`ReplyCard.svelte`), roomier card:
- Header (omitted when `rootPost.status` is set): community avatar `rootPost.community.avatar`, then two lines: the reason ("Reply to your post", "Reply to your comment", "Mentioned you") and `communityMention(rootPost.community)` (`src/lib/app/util/community.ts`, `!name@origin`). Relative `record.createdAt` (else `sortAt`) on the right.
- Root post card (`NotificationPostCard.svelte`, static, Kelp compact post look): `rootPost.author` avatar and `@handle` with the relative `rootPost.createdAt`; `rootPost.title`; `stats.score` and `stats.commentCount`; a tile with `rootPost.thumbnail` or the text-post icon. Each part is omitted when absent; malformed `author`, `createdAt` or `stats` are dropped one by one at the boundary. When `rootPost.status` is set: the placeholder muted and italic in the title position, a text tile, no meta or stats.
- Quoted bubble, indented: author avatar, author name and `@handle` line (no handle line for DID-only), `record.excerpt` or the placeholder when `record.status` is set. For a `mention` whose `record` is a post, the excerpt is shown only when it differs from `rootPost.title`. When the bubble text would equal the title-position placeholder, it is not shown again.
- Quick Reply: a "Reply" button (name "Reply to <author name>", `aria-expanded`), a sibling after the row link, opens `CommentForm.svelte` below the card. Root = `rootPost`; parent = `record` when it is a comment, else none (sent as parent = root). Success closes it and focuses the button; Cancel closes it. Absent when `rootPost.status` or `record.status` is set or while concealed.
- Visible gap between cards.

**Both kinds**: unread rows (`isRead` false after "Seen state") get a subtle tint from existing tokens and carry `data-unread="true"`. The link's accessible name reads like the row: upvote "<names sentence> upvoted your post|comment: <preview>. <time>"; reply "<name> replied to your post|comment in <!community>: <excerpt>. <time>"; mention "<name> mentioned you in <!community>: <excerpt>. <time>"; the community part is dropped when the header is hidden or has no community (decision 27), the `: <preview|excerpt>` segment is dropped when that text is absent and no placeholder applies (a post mention's excerpt equal to `rootPost.title` counts as absent, as on the card), and placeholders read as their copy. A missing `author` reads as "Unknown user" (decision 26).

### Sensitive content
- A reference is sensitive when `hasNSFWLabel(ref.labels)` (`src/lib/feature/post/content-labels.ts`) is true for `rootPost`, `subject` or `record`. A row with any sensitive reference is concealed when `settings.nsfwBlur` (`src/lib/app/state/settings.svelte.ts`) is true; a reply under an NSFW post carries the label on `rootPost` only and still conceals the whole row.
- Concealed: every text (title, preview, excerpt), every thumbnail and the root post card (author, time, stats) in the row, replaced by a banner using the `post.sensitive.*` copy and style of `src/lib/feature/post/Post.svelte` ("NSFW Content", "Show"). Quick Reply is hidden while concealed. The header (who, what, community, when) stays visible.
- The Show button is a sibling of the row link, never inside it, with `aria-expanded` and `aria-controls`. A concealed row's link name is the Row design formula without its `: <preview|excerpt>` segment; titles and thumbnail alt are never part of a link name, concealed or revealed. After Show, the full formula applies. Show reveals that row only; reveal state is a set of row identities owned by the list state, kept while the page is mounted, carried by a return restore (decision 17), and cleared on an owner reset (logout or a different account; see Session ownership).
- Community content warnings are not applied (backend does not send them).

### Settings
- A Notifications section at `/settings/notifications` (`src/routes/settings/notifications/+page.svelte`), added to the `Tabs` in `src/routes/settings/+layout.svelte` only when signed in. Signed out it shows a login link (`loginUrl`) and sends nothing.
- Four `ToggleSetting`s (`src/routes/settings/ToggleSetting.svelte`, unchanged), bound with Svelte 5 function bindings to an app-lifetime store `src/lib/feature/notification/preferences.svelte.ts`: "Replies to your posts" (`postReply`), "Replies to your comments" (`commentReply`), "Mentions" (`mention`), "Upvotes" (`upvote`). Loading shows a `Spinner`; a load error shows "Could not load notification settings." with Retry.
- A toggle moves at once (optimistic) and queues `putNotificationPreferences` with only that key. Puts go one at a time in tap order; each success replaces the stored object with the full returned one, and the display is that object with still-pending values on top. A failure drops that change (the toggle reverts) and toasts "Could not save notification settings." or, for `AccountNotIndexed`, "Your account is still being set up. Try again in a minute." No toast for an expired-session 401.
- The queue lives in the store, not the page: leaving `/settings` mid-save keeps sending under the same session, and returning shows the pending and saved values without starting a second queue. A session key change (expiry and same-generation revival included) bumps the preferences request epoch, empties the queue and the stored object before anything else is sent, drops the in-flight latch, and reloads preferences when the new key is authenticated; a load or put completion from an earlier epoch changes nothing, releases nothing and shows no toast; nothing queued under account A is sent with account B's cookie.
- Preferences load only in the browser: a server render of `/settings/notifications` sends no `social.coves.notification.*` request and renders no fetched values.
- Each successful save refetches the unread count.

### Code map (`src/lib/feature/notification/` unless noted)

- `session.ts`: `notificationSessionKey()` (`${did}|${sessionGeneration}`) and `createRequestEpoch()` (`advance`, `snapshot`, `isCurrent`). A response applies only when its send-time key and epoch are both current. Each store detects key changes itself via `$derived(notificationSessionKey())` in an `$effect.root`.
- `log.ts`: `logNotificationFailure(nsid, error)` logs NSID, HTTP status and `errorName` for `XrpcError`, else `kind: 'non-xrpc'`. Every notification failure goes through it. Never log a URL, cursor, body, `sortAt`/`seenAt`, URI or the session key.
- `preferences.svelte.ts`: `notificationPreferences` (`status`, read-only `values`, `start()`, `retry()`, `set(key, value)`). `set()` is the only writer; bind toggles with function bindings, never a plain `bind:checked`. `start()` is idempotent (later calls get a no-op stop). Each epoch-current put success refreshes the unread count.
- `unread.svelte.ts`: `unreadNotifications` (`count`, `start()`, `refresh()`, `noteNavigation(pathname)`, `onAcceptedRefresh(listener)` emitting `{key, sequence, count}`). Signed in means `profile.isAuthenticated && profile.sessionGeneration !== undefined`. A refresh during an in-flight request is absorbed, not queued. 30 s poll while visible, plus focus, visibility and navigation to exactly `/notifications`. The badge is never zeroed optimistically; any count > 99 renders "99+".
- `rows.ts`: `parseNotificationRows` (skips invalid rows, keeps sparse ones, validates AT-URIs and actors), `notificationIdentity`, `notificationAuthor`, `notificationRootRef` (sanitized community; `name === ''` means no community), `notificationHref`, `placeholderCopyKey`, `isSensitiveRow`, `upvoteSentence`, `notificationLinkName(row, {time, concealed})`, `replyRecordText`, `upvoteSubjectText`, `uniqueRows`, `isCommentUri(uri)` (whether a URI names a `social.coves.community.comment` record). Root post card parts are validated one by one and a malformed part is dropped in a shallow copy: `author` needs a valid DID and a string `handle` (optional string `displayName`, `avatar`), `createdAt` must parse, `stats` needs a safe-integer `score` and nonnegative safe-integer `upvotes`, `downvotes` and `commentCount`. Header, link name and href must all derive from these helpers, never from raw `row.rootPost.community` or labels. Not validated: `cid` (Quick Reply checks it itself), avatar/thumbnail URL schemes (gate images through `isWebUrl`).
- `timestamp.ts`: `compareNotificationTimestamps` (throws on unparseable input; never pass it straight to `sort`), `pageOneWatermark`, `laterPageIsRead`, `usableDate`. Parsing is strict RFC 3339; lowercase `t`/`z` or a missing offset counts as unparseable. The raw server string is what is sent.

### Gotchas

- Boot order: `profile.current` is restored before the root layout's `syncFromServer` sets `sessionGeneration`. Stores gate on `sessionGeneration !== undefined`, or a hard load sends requests twice.

- Firefox pages in one Playwright context all report visible, so hidden-tab paths are unit-tested only.
